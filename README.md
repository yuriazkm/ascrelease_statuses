# Сервис «Статусы»

Личный список отслеживаемых приложений. Доступ выдаётся командам отдельно от
Pipeline через раздел «Доступ к Статусам» в админ-панели. Администраторы имеют
доступ автоматически, но также видят только свой список отслеживания.

## Поведение

- При открытии показываются все приложения, добавленные текущим пользователем.
  Пустой список предлагает добавить приложения. Поиск работает по почте,
  названию и bundle ID; есть фильтр статусов.
- «Из базы»: выбрать доступный аккаунт, загрузить его приложения из Apple,
  отметить нужные и добавить. На аккаунты распространяются существующие правила
  доступа команд и объединённых команд.
  Аккаунты можно искать по почте/названию, приложения — по названию/bundle ID.
  Фильтрация приложений сохраняет уже отмеченные пункты.
  Загрузка выполняется отдельным worker: браузер ставит задание в очередь
  коротким POST и проверяет результат GET-запросами раз в 2 секунды. Основной
  веб-процесс не ждёт подключения к прокси или ответа Apple.
- «Новый аккаунт»: сохранить в нашей БД почту, прокси, Key ID, Issuer ID и файл
  `.p8`, затем выбрать приложения. Это **не создание приложения в Apple**.
  Уже существующие аккаунты не перезаписываются.
- Приложения и их версии хранятся отдельно от аккаунтов. Отслеживание связано
  с ID пользователя: участники одной команды настраивают разные списки.
- В строке показывается последняя по дате создания незаменённая версия каждой
  платформы. Все версии и последние 100 уведомлений доступны в истории.
- Статус относится к **версии приложения**, а не к доступности приложения в
  отдельных странах. Дата «Проверено» означает успешное чтение ASC API;
  «Изменено» берётся из уведомления Apple, если оно получено.
- Удаление из списка не удаляет аккаунт, приложение или историю. Пока приложение
  отслеживает другой пользователь с доступом, вебхук продолжает работать.
  После удаления последнего отслеживания обработчик отключает только наш вебхук.
  Чужие вебхуки не изменяются. Отключённый вебхук можно использовать повторно.

## Официальный API

Используются существующий ASC API key и общий клиент с маршрутизацией через
прокси аккаунта и VPN при необходимости. Веб-логин Apple и 2FA не требуются.
У ключа должны быть права на приложение и управление вебхуками (Account Holder,
Admin или App Manager согласно документации Apple).

- `GET /v1/apps`, `GET /v1/apps/{id}/appStoreVersions`.
- `GET /v1/apps/{id}/webhooks`, `POST /v1/webhooks`, `PATCH /v1/webhooks/{id}`.
- `POST /v1/webhookPings` для проверки приёмника.
- Подписка: `APP_STORE_VERSION_APP_VERSION_STATE_UPDATED`.
- Входящее событие: `appStoreVersionAppVersionStateUpdated`, версия схемы 1.

Источники:
[настройка и подпись уведомлений](https://developer.apple.com/documentation/appstoreconnectapi/configuring-webhook-notifications),
[тип события](https://developer.apple.com/documentation/appstoreconnectapi/webhookeventtype),
[роли и лимиты](https://developer.apple.com/help/app-store-connect/manage-your-team/manage-webhooks/).
Лимит Apple: 10 вебхуков на приложение. При заполненном лимите выводится ошибка;
чужие интеграции не удаляются. Первичное чтение статуса сохраняется даже при
ошибке регистрации вебхука. Нет заявленной гарантии мгновенной доставки Apple.

## Надёжность и безопасность

Вебхук проверяет `x-apple-signature` (`hmacsha256=...`) по исходным байтам тела.
Секрет индивидуален для приложения, зашифрован `ASC_DATA_ENCRYPTION_KEY` и не
возвращается браузеру. Без верной подписи уведомление не принимается.
Ответ 204 отдаётся только после сохранения в PostgreSQL. Повтор одного event ID
не создаёт новых событий или заданий.

Известная версия обновляется сразу из подписанного события. Запоздавшие события
не откатывают более новую сохранённую информацию. После события выполняется
сверка с официальным API; новые ID версий принимаются только после подтверждения
их принадлежности приложению через API. Учитывается короткая задержка согласования
состояния на стороне Apple. Последний известный статус не удаляется при сетевой
ошибке; ошибка показывается отдельно.

Очередь заданий, история и списки хранятся в БД. Ошибки повторяются с паузами
15, 30, 60 секунд и далее до часа. Прерванное задание подхватывается после истечения
10-минутной аренды; одна операция ограничена 240 секундами. Раз в 6 часов выполняется
страховочная сверка, а не постоянный частый опрос Apple. Кнопка обновления ставит
проверку в очередь немедленно. После добавления первая проверка ставится
автоматически, с приоритетом перед плановыми проверками уже известных статусов.
До первого результата отображается «Получаем статус...», страница читает нашу
БД каждые 2 секунды, затем каждые 10 секунд. Это не дополнительные запросы в Apple.

Загрузка списка приложений ограничена 180 секундами непосредственно работы с
Apple (ожидание в очереди не входит). Ошибка прокси или Apple сохраняется и
показывается в окне выбора. Повторное нажатие во время загрузки подключается к
существующему заданию. После ошибки можно запустить новую попытку. Прерванное
задание подхватывается после 5 минут, максимум 3 запуска после аварий. Обычные
ошибки соединения уже повторяются сетевым клиентом, затем выдаётся конечная ошибка.
Очереди загрузки списка и сверки статусов обрабатываются по очереди, чтобы одна
не вытесняла другую. Закрытие окна прекращает опрос, но не удаляет задание из БД.

После обновления с синхронной загрузки необходимо перезапустить **оба** сервиса:
`asc` (миграция новой таблицы) и затем `asc-statuses-worker`. Увеличивать таймауты
Cloudflare/nginx/Gunicorn для загрузки списка приложений не требуется.

Лимит списка: 500 приложений на пользователя. При отзыве доступа команды
отслеживание приостанавливается, если нет других пользователей с доступом.
Ключи новых аккаунтов сохраняются с правами 0600 по принятой в проекте схеме;
их каталог не должен раздаваться веб-сервером.

## Развёртывание на сервере

1. Развернуть код и перезапустить основной `asc` сервис. `init_db()` автоматически
   создаёт новые таблицы; ручные SQL-команды не нужны. Рекомендуется резервная
   копия БД перед развёртыванием (штатный deploy.sh её делает).
2. Добавить в `/var/www/asc/app/.env`:

   ```dotenv
   ASC_STATUSES_PUBLIC_URL=https://ascrelease.ru
   # Необязательно, ниже значение по умолчанию:
   ASC_STATUSES_KEY_DIR=/var/www/asc/uploads/p8/statuses
   ```

   Не менять существующий `ASC_DATA_ENCRYPTION_KEY`. Обработчик использует те же
   `ASC_DB_*`, ключ шифрования и настройки VPN, что основной сервис.
3. Установить отдельный обработчик:

   ```bash
   sudo install -d -o www-data -g www-data -m 0700 /var/www/asc/uploads/p8/statuses
   sudo cp /var/www/asc/app/statuses/asc-statuses-worker.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl restart asc
   sudo systemctl enable --now asc-statuses-worker
   sudo systemctl status asc-statuses-worker --no-pager
   ```

   Пути unit-файла соответствуют существующему deploy.sh. Если venv или проект
   расположены иначе, изменить `WorkingDirectory` и `ExecStart` перед установкой.
   `.env` читает Python; дополнительных переменных в unit не требуется.
   Последующие штатные deploy.sh останавливают и запускают установленный worker.
4. Входящий `POST /api/statuses/webhooks/<token>` должен доходить до Flask через
   HTTPS. Существующего проксирования `/api/` обычно достаточно. Для этого пути
   не должно быть Basic Auth, JS/CAPTCHA challenge или проверки пользовательской
   сессии в nginx/Cloudflare. Не отключать защиту сайта целиком. Подпись проверяет
   приложение; тело и заголовок `x-apple-signature` нельзя изменять.
5. В админ-панели выдать команде доступ к «Статусам». Добавить одно приложение.
   Дождаться статуса и пометки «Вебхук: подключён». Пока тестовое уведомление не
   пришло, отображается «ожидается тестовое уведомление». При ошибках проверить:

   ```bash
   sudo journalctl -u asc-statuses-worker -n 100 --no-pager
   ```

Регистрация реального вебхука происходит только при добавлении приложения и
запущенном worker. Локальные тесты не регистрируют вебхуки в Apple.

## Проверка

Из корня репозитория (с установленными зависимостями):

```bash
PYTHONPATH=app python -m unittest discover -s tests
node --test tests/test_statuses_frontend.cjs
ASC_STATUSES_TEST_DSN='dbname=asc_statuses_test user=... host=127.0.0.1 port=5432' \
  PYTHONPATH=app python -m unittest discover -s tests -p 'test_statuses_postgres.py'
```

Вторая команда предназначена для отдельной тестовой БД. Тесты создают уникальную
временную схему и удаляют только её. Покрыты разделение личных списков, подписи,
дубликаты, порядок событий, ошибки API, пагинация, права и сохранность очереди.
